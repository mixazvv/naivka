# План развития Naivka

Основа: «Naivka — идеи развития и техническое задание», версия 1.0 от 01.11.2026.
Исходный код проверен на коммите `5eb2d82` (VERSION: 2.24.1).

## Первый PR: часть этапа 0

- `lifecycle.go`, `main.go`: необратимое намерение выхода, отмена активного
  подключения, проверка поколения ожидающих подключений и рестартов. Quit
  дожидается очереди lifecycle перед очисткой, без прежнего обхода mutex через 5 с.
- `core.go`, `clash.go`: контекст отмены проверки конфига и ожидания Clash API;
  остановка дочернего процесса и вспомогательного Xray при отмене.
- `selfupdate.go`: legacy EXE выбирается по runtime.GOARCH, переименование
  программы не меняет архитектуру обновления. Неподдерживаемая архитектура
  не получает случайный EXE.
- `.github/workflows/ci.yml`: существующие race, vet и современные Windows-сборки
  дополнены компиляцией legacy на Go 1.20.14 (amd64/386); публикации релизов нет.

Тесты используют отдельные временные каталоги, локальные HTTP-серверы и
процесс-заглушку вместо VPN. Они не доказывают отсутствие сетевых утечек на Windows.
Весь запуск компонентов пока не стал отменяемым: например, запущенная синхронная
операция zapret должна завершиться до финальной очистки Quit. Время выхода поэтому
может быть больше прежних 5 секунд; очистка больше не конкурирует с подключением.
Существующая система failover ещё не переведена на общий координатор.

### Проверки перед слиянием

1. Проверить CI, включая Go 1.20 legacy (amd64/386).
2. На Windows 10/11 начать подключение с медленной проверкой/загрузкой правил,
   затем нажать «Отключить»; убедиться, что ядро завершилось и не подключилось снова.
3. Повторить с выходом из трея во время подключения, повторным нажатием подключения,
   включённым watchdog, системным прокси, TUN и режимом «Только zapret».
4. Проверить повторное явное подключение после отключения и штатную работу Xray.
5. На Windows 7/8 переименовать 32-битный EXE, проверить выбор 32-битного
   обновления; отдельно проверить 64-битный EXE с `32` в имени.

## Исходное требование: завершение этапа 0

Подтверждение готовности новой копии при самообновлении и проверяемый откат.
В исходной версии `cmd.Start()` подтверждал только создание процесса; `.old` удаляется
новой копией слишком рано. Простого ожидания недостаточно: `--replace` ждёт
завершения старого процесса, а старый процесс должен сохранить возможность отката.
Требовался отдельный протокол передачи управления (или помощник), тайм-аут, проверка
идентичности новой копии и сохранение `.old` до подтверждения.

Тесты: ошибка запуска, падение до готовности, зависание, успешное подтверждение,
ошибка отката, сохранение пользовательского отключения во время обновления.
Проверка на реальной Windows обязательна, включая заблокированные EXE,
портативный режим, UAC и legacy. Старый процесс не должен повторно включать VPN
после ручного отключения. Обновление и выпуск релиза — разные операции.

## Дополнение: первый срез read-only диагностики

Ветка `codex/repair-diagnostics` основана на PR этапа 0. Новые API:
`POST /api/repair/start`, `GET /api/repair/status`, `POST /api/repair/cancel`.
Используются существующие token/Host-проверки. Отмена требует operationId;
повторный запуск во время операции возвращает REPAIR_BUSY. Операция имеет общий
тайм-аут 30 с; отдельная HTTPS-проба — 5 с. Disconnect/Quit отменяют диагностику.
Смена поколения, конфигурации или временного failover делает итог устаревшим.
В интерфейсе: Сводка → Проверить сайт → Восстановление соединения.

Это ещё не вся первая фаза раздела 6: проверяются наличие адаптера, Clash API
и два HTTPS-адреса через настроенный локальный прокси. Прямой интернет и DNS
отмечаются UNKNOWN, резервные серверы не проверяются. Один успешный URL не
означает отказ другого сервера. TUN-путь и реальный пользовательский outbound
этими пробами не доказываются. Автоматических исправлений и confirm API нет.
Отчёт содержит только ID и коды проверок, без адресов, ошибок транспорта и секретов.

Следующие необходимые изменения: отдельные контролируемые DNS-пробы, независимые
служебные входы для резервов, ревизии ручного выбора/маршрута для обнаружения
изменений туда-обратно, интеграция с общим журналом и полноценные браузерные тесты.

## Фундамент интерфейса

Ветка `codex/ui-foundation` поверх read-only диагностики добавляет `experience`:
`effects` (off/low/balanced/full), `sound` (off/quiet/digital/retro), `volume`
(0–100), `atmosphere` (off/auto/morning/day/evening/night).
По умолчанию звук и атмосфера выключены, интенсивность — balanced.
Внешний вид → Эффекты и звуки позволяет менять их без сетевого перезапуска.
Настройки нормализуются, сохраняются и исключены из сетевого fingerprint.

`web/experience.js` содержит события переходов подключения и смены сервера,
общую политику reduced motion/скрытого окна и локальную атмосферу времени суток
с сезонными частицами. Подписки возвращают функцию отписки. Первое наблюдение
не вызывает звука. События не содержат сетевых адресов или текстов ошибок.
Звуки синтезируются Web Audio, соблюдают ограничения autoplay, cooldown 3 с,
скрытое окно и мгновенное отключение. Сторонние аудио/погодные сервисы не нужны.
Отдельных звуков котёнка пока нет — его реакции остаются беззвучными.

Существующие design/branches/globe/pet/wall используют одну политику движения;
ветви перестают бесконечно запрашивать кадры в выключенном/скрытом состоянии,
но обновляют статичную схему при изменении данных. Количество частиц SVG,
ветвей, глобуса и атмосферы зависит от интенсивности. Проверка экономии батареи
и замеры нагрузки на реальной Windows ещё необходимы. Отдельный нативный котёнок
на панели задач этим JS-контроллером пока не управляется.

Проверено: race-тесты Go, vet, компиляция Windows amd64; браузерные experience,
pet и branches; полный settings.browser.cjs прошёл повторно (первый запуск дал
сбой сохранения порта раздачи). Новый браузерный тест проверяет события без дублей,
reduced motion, настройки интенсивности и локальное определение зимней ночи.
Обязательны ручные проверки аудио, видео/GIF-фонов и скрытия WebView2 на Windows.

## Альтернативные схемы

`codex/route-diagrams` добавляет опциональные `experience.diagram`:
branches (по умолчанию), orbit и tree. Обе новые схемы читают тот же объект
phase/lanes/top и callbacks, что существующие ветви. Перенос сервиса/процесса
идёт через существующий onDrop, выбор — через onPick/onNode. Отказ сохранения
не меняет изображаемый путь. Успешный перенос временно отображается до обновления
трафика, как в ветвях. Скрытые сервисы открываются в списке соединений.

Это базовые интерактивные схемы: ограничено число подписей, позиции стабильны,
кнопки доступны с клавиатуры, фон SVG не создаёт постоянных циклов анимации.
Толщина линии соответствует трафику; геометрия не изображает задержку.
Пока не добавлены отдельные орбитальные узлы всех сохранённых серверов,
направленные анимированные потоки и плавная интерполяция раскладки. Перенос
со внешней полки процессов не подключён; перенос элементов внутри схемы работает.
Пиксельная тема сохраняет собственную существующую схему.

Проверено: race, vet, Windows amd64; браузерный тест выбора узла, Enter,
успешного/отклонённого переноса, смены режима, повторного update и teardown.

## Конструктор главного экрана

`codex/home-layout`: Внешний вид → Главный экран → Настроить экран.
Реестр включает статус/сервер, уведомления, схему, управление, скорость, IP,
сеанс, подсказку подключения и активность. В редакторе доступны перетаскивание,
кнопки выше/ниже, ширина 1–3 колонки и видимость необязательных карточек.
Шаблоны: Стандартный (исходный интерфейс), Минимализм, Мониторинг; изменения
дают собственную раскладку. Узкое и широкое окно сохраняют отдельный порядок.

Хранение: layout.version=1, wide/narrow — массивы ID/span/hidden. Неизвестная
версия сбрасывается к стандартной, неизвестные/повторные ID отбрасываются,
недостающие виджеты возвращаются, размеры ограничиваются. Статус, уведомления,
подключение и сетевое управление всегда видимы. Произвольного HTML в раскладке нет.
Закрытие редактора без изменений не меняет сохранённый режим. Сброс восстанавливает
исходный CSS. Сетевая конфигурация не зависит от раскладки.

Проверены Go-нормализация, миграция неизвестной версии, сохранение и fingerprint;
браузерные шаблоны/защита подключения/сброс. Нужна ручная проверка реального
WebView2 и всех сочетаний DPI/размеров. Это сеточный редактор порядка и ширины,
пока без свободного изменения высоты карточек мышью и выбора произвольных ячеек.


## Подтверждение самообновления и откат

`codex/update-readiness` реализует протокол помощника из сохранённого `.old`.
Он получает конфигурацию через закрытый stdin-канал и дожидается EOF исходного
процесса. HTTP-проверка старого процесса не используется как доказательство выхода.
Новая копия получает одноразовый callback через переменную окружения, которая
сразу удаляется; помощник проверяет токен, PID и точную версию. На готовность
выделено 60 с, затем выдерживается 1 с стабильности. Готовность означает рабочий
локальный API и созданный UI-хост (трей), а не полностью загруженную страницу
WebView2 или успешное VPN-подключение.

До подтверждения новой копии не запускаются фоновые службы/автоподключение,
не удаляется `.old` и не обновляется соседняя debug-копия. При раннем падении,
ошибке запуска или тайм-ауте помощник останавливает кандидата, возвращает EXE
и запускает прежнюю версию. Намерение подключения хранится отдельно и читается
повторно перед подтверждением/откатом. Ручное отключение в любой копии отменяет
переподключение. Обычный выход отменяет переход; если выход выбран в кандидате,
старый EXE восстанавливается без повторного открытия приложения. AutoConnect
не переопределяет это решение. Поколение повторно проверяется перед resume.

Если готовность/завершение остановки неоднозначны либо откат файлов не удался,
неподтверждённые резервный EXE и запись передачи сохраняются. Автоматическая
очистка не удаляет их; следующий update не перетирает существующую `.old`.
Такая ситуация требует ручного восстановления, а не удаления маркеров вслепую.
После разрешения commit-ответа автоматического отката уже нет: новая копия могла
получить управление системным прокси. Отчёт содержит только фиксированный код;
UI показывает понятное объяснение, журнал — код для диагностики.

Проверки: реальные тестовые процессы с правильным/неверным PID, токеном, версией,
зависание, падение до готовности и между ready/commit, ошибки запуска/отката,
ручное отключение/выход в исходной и новой копии, ожидание EOF, сохранение backup,
запрет повторного подключения по старому поколению. Linux smoke проверяет обычный
запуск API и выход без VPN. Нужны реальные Windows-проверки по отдельному чек-листу.

Новый протокол применяется к обновлениям, инициированным версией с этим кодом.
Само обновление с прежней 2.24.1 всё ещё инициирует старый updater; ему нельзя
задним числом добавить помощника. В новой версии обычная очистка старого EXE
также отложена до доступности API/UI-хоста, но обратный откат старым updater
не обеспечивается. VERSION и релизные файлы не меняются этим PR.

## Привычки, редкие события и игры котёнка

`codex/pet-habits-games` расширяет текущий pet.js, сохраняя атлас и физику.
Новый pet-mind.js не имеет собственных таймеров, сетевых команд и DOM-операций.
Энергия/любопытство/комфорт/игривость меняют веса существующих действий; знакомые
опоры получают небольшой приоритет. Сон, скрытое окно, выключенные эффекты,
системное reduced motion и открытые панели не приводят к штрафу за отсутствие.

Постоянная память хранится в settings.petMemory, поскольку origin WebView зависит
от меняющегося порта API. Версия 1 содержит дату первого знакомства, общий cooldown,
счётчики только восьми известных UI-поверхностей и четыре фиксированных события.
Go отбрасывает неизвестные ключи, ограничивает счётчики и даты; память исключена
из сетевого fingerprint. Запись выполняется только при изменениях, не чаще раза
в минуту, с финальным сохранением при отключении талисмана. Есть сброс привычек.

Редкие события: ночная звезда, стабильная сессия, найденная игрушка, годовщина.
Не ранее десяти минут после mount, не чаще раза в час в целом и раза в сутки
для конкретного события. Они запускаются только в свободном состоянии и используют
существующие рисунки. Они не вмешиваются в игру, перенос котёнка и критические
реакции сети. Сайты, домены и данные соединений в память не попадают.

Внешний вид → Котёнок: явные «Догонялки»/«Клубок» продолжаются до 20 с (остановка
на ближайшем шаге контроллера). Используется существующий прыжок по текущей опоре;
игрушка не перехватывает указатель. Клавиша, щелчок, фокус поля ввода, диалог,
смена экрана/отключение/сетевая ошибка, reduced motion, скрытие и unmount завершают игру.
Обычное изменение интенсивности трафика игру не прерывает.
Существующие карточки дополнены data-pet-surface; запрещённые зоны и inert/modal
не выбираются как цели. Наблюдатель диалогов отключается при unmount.

Этот блок относится к котёнку главного окна: нативный режим панели задач остаётся
на прежнем контроллере. Игры в нём недоступны; полноценный свободный персонаж
рабочего стола по пункту 22 остаётся отдельным этапом. Игры сейчас ограничены
текущей опорой; прятки и отдельная охота за точкой не добавлялись. Новых кадров нет.

Проверки: Go-нормализация/приватность/сохранение и fingerprint, race, vet,
компиляция Windows amd64 и legacy 386; pure Node-симуляция добавлена в CI;
браузерные pet, pet-behavior и полный settings. Реальные WebView2/DPI и нагрузку
всего окна нужно проверить отдельно; тесты в Chromium не заменяют Windows.


### Продолжение №31/34: разовый отчёт собственного Linux VPS

«Свой сервер» → карточка сохранённого сервера → «Состояние VPS» →
«Проверить сейчас». Открытие окна само по себе не подключается по SSH.
Используется существующая проверка подтверждённого fingerprint, запрос пароля/ключа
и соединение с 20-минутным сроком простоя из блока друзей. Секреты не сохраняются.
Друзья и отчёты сериализованы; VPN-подключение от отчёта не зависит.

Фиксированный встроенный `server/vps-report.sh` выполняется через `sh -s`, без
подстановки адресов/путей/команд из запроса, sudo, установки агента или записи файлов.
Linux с /proc: CPU за одну секунду, load1/число CPU, RAM (MemAvailable), корневой диск,
uptime, суммарные RX/TX интерфейсов кроме lo. Сетевые значения — счётчики, не скорость;
возможен повторный учёт туннелей. Недоступная метрика остаётся неизвестной.
Службы systemd: sing-box, xray, naivka-caddy, x-ui и их автозапуск.

Частичный аудит: эффективные общие значения sshd -T (root/password; Match и
keyboard-interactive/PAM не оценены), состояние UFW (не полнота правил/другие firewall),
Unix-права /etc/sing-box/config.json (без ACL/владельца), срок окончания только
/etc/sing-box/naivka-hy2.crt (без доверия/имени/начала срока и сертификатов панелей).
Обновления ОС и внешняя доступность портов явно UNKNOWN. Неизвестные значения и
недостаток прав не превращаются в успешную проверку. Исправления не выполняются.
Это первый ограниченный этап №31/34, не завершение всей приёмки: нет опроса по таймеру,
скорости сети, поддержки всех панелей/дистрибутивов, полного аудита и истории на диске.

После авторизации — общий тайм-аут отчёта 30 с, включая открытие SSH-канала.
Тайм-аут/отмена закрывают транспорт, чтобы не оставить зависший NewSession/Run.
TCP и SSH handshake отдельно ограничены 20 с каждый (ранее Timeout ограничивал
лишь TCP). Сырой stdout ограничен 16 КиБ; stderr отбрасывается. API возвращает только
числовые метрики и значения из разрешённых списков, без содержимого конфигураций/логов.
История в памяти окна: пять снимков на сервер, максимум 20 серверов; повторный
щелчок во время запроса не создаёт второй запрос, закрытое окно игнорирует поздний ответ.

Проверки: целевые Go-тесты с race (тайм-аут/отмена/размер/фильтрация/права/авторизация
API без реального SSH), go vet, компиляция Windows amd64 и legacy 386, синтаксис sh/JS.
Pure Node fixture tests/vps-ui.cjs проверяет явный запуск, передачу SSH-авторизации,
дубли кликов, поздний ответ и ограничение истории; включён в CI.
Реальный VPS и настоящий браузер для нового окна в этой итерации не использовались.


### Продолжение №34: локальный кэш обновлений и привязки портов

Отчёт VPS расширен без новых команд записи, sudo, внешних запросов или фонового агента.
Для ID debian/ubuntu из /etc/os-release (файл разбирается как данные, не исполняется)
читаются существующие индексы /var/lib/apt/lists/*_Packages* и `apt list --upgradable`.
Создание pkgcache/srcpkgcache отключено, блокировка отключена. Данные репозиториев
не обновляются, пакеты не скачиваются и не устанавливаются. Возвращаются только
число кандидатов и минимальный/максимальный mtime файлов индексов; имена/версии
пакетов и адреса репозиториев не возвращаются. Отсутствие индексов, ошибка APT или
неизвестный формат дают UNKNOWN; другие ОС помечаются неподдерживаемыми.

Нулевое число кандидатов имеет уровень INFO: это не доказательство актуальности ОС.
UI показывает диапазон дат файлов, отдельно отмечает индексы старше 7 дней и
ограничения проверки: mtime не подтверждает успешное обновление всех источников,
полнота источников и security-обновления не проверены. Даты зависят от часов VPS;
явно невозможные/будущие значения отбрасываются серверной частью.

`ss -H -lntu` даёт локальные TCP LISTEN / UDP UNCONN в сетевом окружении SSH.
Возвращаются только протокол, номер порта и тип привязки (loopback/все интерфейсы/
отдельный адрес); IP-адреса, имена процессов и PID не возвращаются. Дубликаты
объединяются, сохраняется максимум 128 различных записей с явной пометкой усечения.
Успешный пустой результат отличается от ошибки команды/формата. Внешняя доступность
остаётся UNKNOWN: firewall, NAT и отдельные сетевые пространства контейнеров
не оцениваются. Ни нестандартный порт, ни привязка на все интерфейсы сами по себе
не маркируются уязвимостью. Совокупный тайм-аут отчёта 30 с и лимит 16 КиБ сохранены.

Проверки: Go/race на подставных Linux-файлах и командах (включая разрешённые аргументы

Реальные VPS не использовались. Для №31/34 всё ещё остаются опрос при открытой

### №24: умный выбор своих серверов по истории контрольных запросов

«Настройки → Надёжность → Умный выбор своих серверов» — отключаемый режим,
по умолчанию выключен. Раз в минуту при работающем ядре запускается свежий
GroupDelay через sing-box для своих серверов. Полные загрузочные speedtest не
запускаются; кэшированные /proxies history не считаются повторными измерениями.
До первого успешного пакета измерений работает штатный автовыбор ядра.
В режиме «Автовыбор» текущий ответивший сервер закрепляется в основном selector,
затем оцениваются подтверждённые улучшения. При ручном выборе автоматической
оптимизации нет; существующий явный Failover использует оценку для выбора резерва.
Подписка WL, посторонние/удалённые теги и отсутствующие ответы не выбираются.

История ограничена 20 измерениями на свой сервер за 15 минут, только в памяти.
Показатели: успешные контрольные запросы, медиана (для чётного N — среднее двух
центральных), p95 nearest-rank и частота неудач за последние 4 минуты. Успешным
считается положительное значение задержки, полученное через API ядра; это не
измерение ICMP packet loss и не самостоятельная проверка полного пользовательского
пути из мастера ремонта. Общая ошибка API/пакета измерений даёт UNKNOWN и не
записывается как N неудач всех серверов. В успешном ответе GroupDelay отсутствие
тега означает неответившую проверку этого сервера.

Вес скорости неизвестен и исключён: исходные 40/30/10 нормализованы в 50% успешности,
37.5% задержки и 12.5% недавних ошибок. Задержка преобразуется функцией 1/(1+ms/200);
комбинация 70% медианы и 30% p95, причём штраф p95 ограничен тройной медианой, чтобы
один выброс не доминировал. Это стартовая эвристика, а не доказанная оценка скорости.
В окне «Качество серверов» показаны сырые медиана/p95, оценка, количество проверок,
свежесть и карантин; причины принятых решений попадают в ленту событий.

Ответ для выбора должен быть свежим (до 90 с) и последним успешным. Три неудачи
подряд помещают сервер в карантин на 2 минуты после последней неудачи. Для
оптимизации исправного соединения: минимум два последних успешных ответа кандидата,
улучшение на 12 баллов, два подтверждения подряд и выдержка 3 минуты с переключения.
Две неудачи текущего сервера допускают аварийную смену раньше, если резерв дважды
ответил; оставленный сервер получает карантин. Первичное закрепление/аварийный
Failover могут использовать первый свежий успешный ответ. Эти операции сохраняют
Selected в настройках; ручной выбор имеет приоритет. Смена основного selector
использует существующее interrupt_exist_connections ядра.

Все автоматические записи selector проверяют поколение жизненного цикла, желание
быть подключённым, ревизию ручного выбора, конфигурацию, активность WL и secret
текущего процесса ядра. Пробы идут вне блокировок. Перед записью: life.mu →
selectionMu, операция получает контекст life.operation и отменяется при Disconnect.
Окно и Windows-трей используют общий selectServer: ручное действие, пришедшее во
время записи, выполняется последним. Старый замер не применяется после ручной смены,
нового ядра/настроек или отключения. При неприменённой конфигурации автоматика ждёт
переподключения. Изменение только smartSelect не меняет fingerprint ядра.

Failback сохраняет резерв до успешного Select; при ошибке счётчик подтверждений
сбрасывается и действует пауза 2 минуты. При включённой оценке карантин исходного
сервера запрещает ранний возврат. Это исправляет прежнюю потерю состояния резерва
при ошибке переключения, но не заменяет транзакционную проверку пользовательского
пути/rollback из №25 и раздела 6 — этот отдельный этап ещё не закрыт.

Проверки: целевые Go/race сценарии статистики, выброса, выдержки/повторного
подтверждения, аварийной смены, карантина/TTL, ограничений/allowlist, смены ядра,
ручного выбора, pending-конфигурации, отмены HTTP при отключении, общей ошибки API
и неудачного Failback; HTTP выполняется через fake RoundTripper без сокетов/VPN.
Node fixture проверяет подписи уверенности, UNKNOWN скорости и закрытие окна;
включён в CI. go vet для Linux/Windows, компиляция Windows amd64 и legacy 386.
Реальная эксплуатация VPN и браузерное окно в этой итерации не проверялись.
