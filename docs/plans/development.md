# План развития Naivka

Основа: «Naivka — идеи развития и техническое задание», версия 1.0 от 01.11.2026.
Исходный код проверен на коммите `5eb2d82` (VERSION: 2.24.1).

## Первый PR: часть этапа 0

- `lifecycle.go`, `main.go`: необратимое намерение выхода, отмена активного
  подключения, проверка поколения ожидающих подключений и рестартов. Quit
  дожидается очереди lifecycle перед очисткой, без прежнего обхода mutex через 5 с.
- `core.go`, `clash.go`: контекст отмены проверки конфига и ожидания Clash API;
  остановка дочернего процесса и вспомогательного Xray при отмене.
- `selfupdate.go`: legacy EXE выбирается по runtime.GOARCH, переименование
  программы не меняет архитектуру обновления. Неподдерживаемая архитектура
  не получает случайный EXE.
- `.github/workflows/ci.yml`: существующие race, vet и современные Windows-сборки
  дополнены компиляцией legacy на Go 1.20.14 (amd64/386); публикации релизов нет.

Тесты используют отдельные временные каталоги, локальные HTTP-серверы и
процесс-заглушку вместо VPN. Они не доказывают отсутствие сетевых утечек на Windows.
Весь запуск компонентов пока не стал отменяемым: например, запущенная синхронная
операция zapret должна завершиться до финальной очистки Quit. Время выхода поэтому
может быть больше прежних 5 секунд; очистка больше не конкурирует с подключением.
Существующая система failover ещё не переведена на общий координатор.

### Проверки перед слиянием

1. Проверить CI, включая Go 1.20 legacy (amd64/386).
2. На Windows 10/11 начать подключение с медленной проверкой/загрузкой правил,
   затем нажать «Отключить»; убедиться, что ядро завершилось и не подключилось снова.
3. Повторить с выходом из трея во время подключения, повторным нажатием подключения,
   включённым watchdog, системным прокси, TUN и режимом «Только zapret».
4. Проверить повторное явное подключение после отключения и штатную работу Xray.
5. На Windows 7/8 переименовать 32-битный EXE, проверить выбор 32-битного
   обновления; отдельно проверить 64-битный EXE с `32` в имени.

## Следующий PR: завершение этапа 0

Подтверждение готовности новой копии при самообновлении и проверяемый откат.
Текущий `cmd.Start()` подтверждает только создание процесса; `.old` удаляется
новой копией слишком рано. Простого ожидания недостаточно: `--replace` ждёт
завершения старого процесса, а старый процесс должен сохранить возможность отката.
Нужен отдельный протокол передачи управления (или помощник), тайм-аут, проверка
идентичности новой копии и сохранение `.old` до подтверждения.

Тесты: ошибка запуска, падение до готовности, зависание, успешное подтверждение,
ошибка отката, сохранение пользовательского отключения во время обновления.
Проверка на реальной Windows обязательна, включая заблокированные EXE,
портативный режим, UAC и legacy. Старый процесс не должен повторно включать VPN
после ручного отключения. Обновление и выпуск релиза — разные операции.

## Этап 1: общий фундамент интерфейса

Отдельная ветка после этапа 0:

1. Сопоставить существующие циклы `design.js`, `branches.js`, `globe.js`,
   `pet.js`, `wall.js` с общей политикой эффектов; сохранить нынешний вид по умолчанию.
2. Добавить общий поток событий по переходам состояния, без повторов при опросе.
3. Ввести сохраняемые `off/low/balanced/full`, reduced motion и остановку
   декоративных циклов скрытого окна. Не менять сетевой fingerprint ради оформления.
4. Подключить необязательные звуковые темы с исходным состоянием «Без звука»,
   cooldown, отдельной громкостью и немедленным отключением.
5. Добавить локальную атмосферу по времени суток/сезону; сохранить читаемость
   и смысл цветов маршрутов, не запрашивать погоду у сторонних сервисов.
6. Проверить браузерные сценарии, teardown, нагрузку и реальный WebView2.

## Дополнение: первый срез read-only диагностики

Ветка `codex/repair-diagnostics` основана на PR этапа 0. Новые API:
`POST /api/repair/start`, `GET /api/repair/status`, `POST /api/repair/cancel`.
Используются существующие token/Host-проверки. Отмена требует operationId;
повторный запуск во время операции возвращает REPAIR_BUSY. Операция имеет общий
тайм-аут 30 с; отдельная HTTPS-проба — 5 с. Disconnect/Quit отменяют диагностику.
Смена поколения, конфигурации или временного failover делает итог устаревшим.
В интерфейсе: Сводка → Проверить сайт → Восстановление соединения.

Это ещё не вся первая фаза раздела 6: проверяются наличие адаптера, Clash API
и два HTTPS-адреса через настроенный локальный прокси. Прямой интернет и DNS
отмечаются UNKNOWN, резервные серверы не проверяются. Один успешный URL не
означает отказ другого сервера. TUN-путь и реальный пользовательский outbound
этими пробами не доказываются. Автоматических исправлений и confirm API нет.
Отчёт содержит только ID и коды проверок, без адресов, ошибок транспорта и секретов.

Следующие необходимые изменения: отдельные контролируемые DNS-пробы, независимые
служебные входы для резервов, ревизии ручного выбора/маршрута для обнаружения
изменений туда-обратно, интеграция с общим журналом и полноценные браузерные тесты.

## Фундамент интерфейса

Ветка `codex/ui-foundation` поверх read-only диагностики добавляет `experience`:
`effects` (off/low/balanced/full), `sound` (off/quiet/digital/retro), `volume`
(0–100), `atmosphere` (off/auto/morning/day/evening/night).
По умолчанию звук и атмосфера выключены, интенсивность — balanced.
Внешний вид → Эффекты и звуки позволяет менять их без сетевого перезапуска.
Настройки нормализуются, сохраняются и исключены из сетевого fingerprint.

`web/experience.js` содержит события переходов подключения и смены сервера,
общую политику reduced motion/скрытого окна и локальную атмосферу времени суток
с сезонными частицами. Подписки возвращают функцию отписки. Первое наблюдение
не вызывает звука. События не содержат сетевых адресов или текстов ошибок.
Звуки синтезируются Web Audio, соблюдают ограничения autoplay, cooldown 3 с,
скрытое окно и мгновенное отключение. Сторонние аудио/погодные сервисы не нужны.
Отдельных звуков котёнка пока нет — его реакции остаются беззвучными.

Существующие design/branches/globe/pet/wall используют одну политику движения;
ветви перестают бесконечно запрашивать кадры в выключенном/скрытом состоянии,
но обновляют статичную схему при изменении данных. Количество частиц SVG,
ветвей, глобуса и атмосферы зависит от интенсивности. Проверка экономии батареи
и замеры нагрузки на реальной Windows ещё необходимы. Отдельный нативный котёнок
на панели задач этим JS-контроллером пока не управляется.

Проверено: race-тесты Go, vet, компиляция Windows amd64; браузерные experience,
pet и branches; полный settings.browser.cjs прошёл повторно (первый запуск дал
сбой сохранения порта раздачи). Новый браузерный тест проверяет события без дублей,
reduced motion, настройки интенсивности и локальное определение зимней ночи.
Обязательны ручные проверки аудио, видео/GIF-фонов и скрытия WebView2 на Windows.

## Альтернативные схемы

`codex/route-diagrams` добавляет опциональные `experience.diagram`:
branches (по умолчанию), orbit и tree. Обе новые схемы читают тот же объект
phase/lanes/top и callbacks, что существующие ветви. Перенос сервиса/процесса
идёт через существующий onDrop, выбор — через onPick/onNode. Отказ сохранения
не меняет изображаемый путь. Успешный перенос временно отображается до обновления
трафика, как в ветвях. Скрытые сервисы открываются в списке соединений.

Это базовые интерактивные схемы: ограничено число подписей, позиции стабильны,
кнопки доступны с клавиатуры, фон SVG не создаёт постоянных циклов анимации.
Толщина линии соответствует трафику; геометрия не изображает задержку.
Пока не добавлены отдельные орбитальные узлы всех сохранённых серверов,
направленные анимированные потоки и плавная интерполяция раскладки. Перенос
со внешней полки процессов не подключён; перенос элементов внутри схемы работает.
Пиксельная тема сохраняет собственную существующую схему.

Проверено: race, vet, Windows amd64; браузерный тест выбора узла, Enter,
успешного/отклонённого переноса, смены режима, повторного update и teardown.
